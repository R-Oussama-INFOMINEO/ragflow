# RAGFlow Retrieval Architecture & Enhancements

This document explains the functionality of the `retrieval` method available in the `DocumentRagflowAPI` and `SearchRagflowAPI`, and its underlying behavior in the RAGFlow backend (specifically inside the `api/apps/chunk_app.py` and `api/apps/sdk/doc.py` endpoints).

## Core Retrieval Process

The standard retrieval process (called internally via `settings.retriever.retrieval()`) performs the initial search operation. It is responsible for:
1. Embedding the user's question using the configured Embedding Model.
2. Performing hybrid search (combining dense vector similarity with sparse BM25 retrieval) over the specified datasets or document chunks.
3. Ranking the initial chunks based on multiple metrics like `similarity_threshold` and `vector_similarity_weight`.

## Advanced Search Enhancements

The Retrieval API supports several advanced enhancement techniques, which can be enabled via properties in the `RetrievalRequest`.

### 1. Table of Contents (TOC) Enhancement (`toc_enhance`)

**What it does:**
When `toc_enhance=True` is provided in the request, RAGFlow uses Table of Contents data extracted during document parsing to improve search results.

**How it works:**
- It calls `settings.retriever.retrieval_by_toc(...)`.
- The system feeds the user's question and the initially retrieved chunks (and their TOC structure) into a Chat LLM.
- The LLM reasons over the TOC hierarchy to filter layout-irrelevant chunks and correctly prioritize or re-order chunks that fall under sections most relevant to the user's query.

### 2. Knowledge Graph Retrieval (`use_kg`)

**What it does:**
When `use_kg=True` is provided, RAGFlow queries the Knowledge Graph associated with the user's documents to synthesize a comprehensive "graph-based" answer chunk.

**How it works:**
- It calls `settings.kg_retriever.retrieval(...)`.
- The query searches for nodes and relationships matching the intent of the question.
- The KG query is passed to the Chat LLM which generates a highly synthesized chunk based on graph relationships.
- **Integration:** This synthesized chunk is injected at the very top of the results list (`ranks["chunks"].insert(0, ck)`). It appears as the most relevant chunk because it provides a summarized, connected-graph answer.

### 3. RAPTOR (Recursive Abstractive Processing for Tree-Organized Retrieval)

**What it does:**
RAPTOR goes beyond flat chunks by summarizing related chunks into hierarchical parent chunks (called semantic trees). When a parent chunk matches the query, RAGFlow guarantees the context isn't lost by recursively fetching its children.

**How it works:**
- It calls `settings.retriever.retrieval_by_children(ranks["chunks"], ...)` at the end of the retrieval pipeline.
- If any of the retrieved chunks is a "parent summary chunk" generated by the RAPTOR model during parsing, this function retrieves the corresponding child chunks.
- This provides the LLM with both the high-level summary (the parent chunk) and the detailed supporting evidence (the child chunks), significantly improving response accuracy for complex reasoning questions.
- **Note on API Parameter**: The RAPTOR behavior triggers automatically on retrieval if RAPTOR data exists for the dataset (meaning `retrieval_by_children` is always executed in the pipeline). The `RetrievalRequest` doesn't explicitly toggle RAPTOR on/off during retrieval; rather, if the dataset was processed with a RAPTOR task (`run_raptor` endpoint), its chunks naturally benefit from this logic during standard search.

## How They Work Together

From the API client's point of view (like using `DocumentRagflowAPI.retrieval`), these features can be enabled simultaneously and form a pipeline sequence inside the RAG backend:

1. **Initial Vector/BM25 Search:** Gathers the top `N` strongest chunk candidates.
2. **TOC Filter/Sort (`toc_enhance`):** Reorganizes these chunks using LLM reasoning over the Table of Contents.
3. **RAPTOR Context Expansion:** Checks all returned chunks and automatically fetches any missing child chunks to guarantee deep context availability.
4. **KG Injection (`use_kg`):** Synthesizes a knowledge-graph-driven chunk and forcefully places it at the very top of the sorted chunks list (Index 0).

All of these are configurable parameters that enhance the final set of chunks returned seamlessly in a single `RetrievalResponse`.

## Additional Search Capabilities

The RAGFlow Retrieval API also supports other search modifiers exposed through `RetrievalRequest`:

- **Cross-Lingual Search (`cross_languages`)**: Translates the user's query into different languages using an LLM before performing the retrieval, allowing cross-lingual document discovery.
- **Keyword Extraction (`keyword`)**: If enabled, uses a Chat LLM to extract vital keywords from the user query before performing the sparse BM25 search step.
- **Metadata Filtering (`meta_data_filter`)**: Pre-filters the documents search space based on exact metadata matching or range constraints before embedding or matching happens.
- **Reranker (`rerank_id`)**: Re-scores chunks globally using a cross-encoder Reranker model fine-tuned for high-accuracy ordering.
- **Highlighting (`highlight`)**: Optionally highlights matching tokens within the returned chunks. Added to `RetrievalRequest` to align with backend functionality.
